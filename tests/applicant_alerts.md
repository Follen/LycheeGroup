# 新申请声音状态机验证

适用范围：`codex/voice-alerts` 的未发布改动。产品行为见 [Product.md](../Product.md) 的“新申请提示”，状态及所有权见 [Architecture.md](../Architecture.md#91-新申请声音状态机与轻量悬浮窗)，成本约束与本次结果见 [perfermance.md](../perfermance.md#124-2026-10-26-新申请声音状态机离线验证)。

## 离线运行

在仓库根目录使用 Lua 5.1：

```powershell
lua tests/runner.lua core group alert_performance ui
lua tests/run_layout_checks.lua
```

`tests/runner.lua` 的默认完整入口也包含 `alert_performance`。

- `group` 使用真实业务模块和原生 API 替身，核对第一次播放、3 秒内新申请静音丢弃且到期不补播、3 秒后真正的新申请再次播放、重复／延迟数据、多人同行、列表可见、静默恢复、权限／招募／音色变化，以及试听句柄与原生静音锁。取消、邀请、拒绝、资料更新、排序和动作失败都不能产生新提醒。
- `alert_performance` 使用真实 Applicants 与 Alerts，按申请数量扩大场景。用 Lua 指令计数比较提醒同步成本；同时检查该路径不请求申请者／成员 API，持续申请及冷却内也不创建声音计时器、候选记录或待播队列。已有展示通知单独计数，不与声音任务混淆。
- `core` 核对默认音色、账号保存、合法选项与按需加载；`ui` 及布局入口核对查看状态与设置交互，各音色右侧的图标只试听对应音色，关闭一行无图标、试听不改变选择、关菜单／切页／关闭停止试听，并覆盖中英文布局。

测试使用独立替身，不访问游戏存档。申请记录与原业务展示任务在场景结束时清理；不需要游戏操作。指令计数证明离线路径的工作量，不代表实际游戏 CPU 时间或音频解码内存。

2026-10-26 当前“不排队、不补播”规则的离线结果：完整 `lua tests/runner.lua` 通过 28,280 项断言、0 个模块失败；`lua tests/run_layout_checks.lua` 的 17 个脚本全部通过，其中设置专项通过 9,885 项检查；63 份产品 Lua 与新探针通过语法检查。1,000 批申请突发只播放首声，声音计时器始终为 0；原业务共用的展示通知任务为 1 个，稳定后为 0。`Alerts:Sync` 没有申请者／成员 API 读取，1 与 1,000 批申请的同步成本比较断言通过。

同日菜单试听调整为各音色右侧的独立图标，设置专项 9,885 项检查、响应式设置 2,335 项检查、group／ui 回归 8,071 项断言及声音性能 28 项断言通过。设置专项覆盖对应音色播放、选择关闭时试听不启用提醒、菜单保持展开、关闭后停止、按钮复用，以及中英文 70%／100%／130% 字号下的文字与图标间距。

## 游戏内验证

`tests/live_applicant_alerts.lua` 提供 60 秒有界观察。前提是 Group 已加载、当前角色正在招募且选择中文语音；让真实玩家正常申请。探针只临时观察本模块的播放入口及申请更新，记录高精度播放调用时间、声道、句柄、试听标记与首次名单遗漏的保留结果，不操作队伍，不替换全局声音函数。完成、取消或超时后恢复本模块函数环境及方法，取消计时器并解除事件。

```text
lycheedev live execute --project <原连接项目> --session <CON-id> --file tests/live_applicant_alerts.lua --request <唯一请求名> --budget-seconds 75 --wait-seconds 30 --policy observation --format json
```

主机等待到期时继续同一 CON 的 `live resume`，直到报告验证且清理完成。用 `plays` 中成功且非试听的调用计算起始间隔，并结合 `newItems`、`listChecks` 和事件判断重复申请；没有真实申请或没有播放记录的窗口不算通过。该观察不测量 CPU、内存或声音在设备上的输出延迟。

1. 打开“设置 → 常规”的新申请提示音下拉菜单，点击各音色右侧图标试听荔枝内置语音和原生提示音，确认菜单保持展开且保存的选择不变；连续点击图标，切音色、切分类与关闭主窗，确认没有叠音或残留试听，并核对两种声音均随游戏对话音量调节。
2. 发布招募，让另一名玩家申请；保持申请列表打开、关闭和浮窗展开各验证一次。首批响一次，单独保留未处理申请不再循环。
3. 在首声后 3 秒内提交多批申请，确认列表正常更新且没有新声音。随后停止申请并等待超过 3 秒，确认截止时和之后均不补播；再提交一批真正的新申请，确认立即响一次。多人同行按一批处理。
4. 对已有申请执行取消、邀请、拒绝、资料更新和排序，确认都不触发声音；在 3 秒内被静音的申请即使仍留在列表中，也不会在后续刷新或动作失败时补响。
5. 在首声后的 3 秒内结束并重建招募、转交并恢复队长权限或关闭并重新打开声音；新申请仍受原有间隔约束，旧申请不补播。切换音色后立即来新申请也不能绕过间隔。连续试听不改变真实新申请的间隔。
6. 核对原生眼睛高亮及查看清除仍可用，原生新申请不再叠加循环音；另外验证普通邀请与副本就绪声音保留。结束测试招募，恢复原设置。

当前“不排队、不补播”规则尚未完成上述实机验收。
